# Su-Tech: план доведения программной части до конкурсного релиза

Дата аудита: 20 сентября 2026 года.

## 1. Что уже подтверждено

- Активный расчёт использует суточные `ET0` и осадки Open-Meteo, TAW/RAW,
  выбранное состояние почвы, календарь культуры и КПД способа полива.
- Фактический порог равен `min(технологический порог, RAW)`.
- Экономика сравнивает один текущий дефицит при одинаковых насосе и тарифе.
- Запятая в десятичных значениях площади и параметров насоса принимается.
- Поле, дневной баланс и подтверждённый полив сохраняются транзакционно.
- Повторный расчёт одной даты не начисляет дефицит второй раз.
- Одновременные запуски планировщика создают одну запись и одно уведомление.
- Старый файл базы мигрирует без потери существующих полей.
- После подтверждения полива следующий день начинается с нулевого дефицита.
- Карта, контур, площадь, теплица, другая культура и параметры насоса проходят
  автоматический фронтенд-тест.
- Публичный backend отвечает через webhook, Open-Meteo отдаёт живые данные,
  фактический WebApp URL доступен.

## 2. Что мешает считать production полностью готовым

1. Новые коммиты backend ещё не опубликованы на Render.
2. SQLite лежит в файловой системе Render. На бесплатном сервисе она временная:
   состояние может исчезнуть при остановке, рестарте или деплое.
3. Нет программного протокола для стенда: регистрации устройства, телеметрии,
   команд помпе, подтверждения выполнения и аварийных ограничений.
4. Нет таблиц и интерфейса для фактических измерений эксперимента: литры,
   энергия, влажность почвы, состояние растений и контрольная группа.
5. Автоматический расчёт запускается внутри одного web-процесса. Для одного
   экземпляра это работает, но после масштабирования понадобится блокировка
   заданий через общую базу.
6. Рис, промывка засолённых почв и ET0 теплицы намеренно требуют отдельных
   входных данных. Их нельзя выдавать за полностью автоматические режимы.

## 3. Порядок реализации

### Этап A. Надёжное облачное состояние

1. Выбрать постоянную PostgreSQL и добавить `DATABASE_URL`.
2. Перенести `users`, `history`, `fields`, `field_daily_balances`,
   `irrigation_events` и `report_explanations` через слой репозитория.
3. Добавить версионированные миграции и команду переноса текущей SQLite.
4. Расширить `/health`: готовность базы, версия схемы, дата последнего удачного
   ежедневного обновления. Секреты и координаты в ответ не включать.
5. Добавить резервный экспорт и срок хранения объяснений отчёта.

**Готово, когда:** рестарт и новый деплой не удаляют поле, историю и выбранный
язык; миграционный тест и тест восстановления проходят автоматически.

### Этап B. Поле как самостоятельный объект

1. Дать полю имя и постоянный UUID. Координаты, площадь и культура станут
   редактируемыми свойствами, а не частью идентификатора.
2. Добавить в WebApp экран «Мои поля»: открыть, изменить параметры, посмотреть
   текущий дефицит и журнал.
3. Разделить действия «изменить параметры» и «заново оценить влажность», чтобы
   повторная отправка формы не выглядела как обычное ежедневное обновление.
4. После «Поле полито» показывать актуальное состояние `0 мм` и отдельную запись
   события, сохраняя расчёт до полива в историческом журнале.

**Готово, когда:** фермер однозначно выбирает нужное поле, изменение площади не
создаёт дубликат, а все операции проверяют владельца.

### Этап C. Надёжный ежедневный расчёт

1. Хранить дату и результат каждой попытки получения погоды.
2. Добавить ограниченные повторы Open-Meteo с паузой и статус «данные погоды
   временно недоступны» без выдуманных значений.
3. Выполнять одно дневное задание на поле через уникальный ключ в PostgreSQL.
4. Отправлять уведомление при переходе статуса, а не повторять одинаковое
   предупреждение каждый день без контекста.
5. Добавить журнал ошибок без токенов и персональных данных.

**Готово, когда:** падение Open-Meteo, рестарт в середине задания и два
одновременных процесса не теряют и не удваивают баланс.

### Этап D. API физического стенда

Новые сущности:

- `devices`: поле, идентификатор, хеш ключа, состояние и последняя связь;
- `sensor_readings`: время, влажность почвы, температура, влажность воздуха,
  освещённость и расход воды;
- `pump_commands`: команда, режим, максимальная длительность, статус и автор;
- `pump_events`: фактические начало, конец, литры, энергия и причина остановки;
- `calibrations`: сухое/влажное значение датчика и коэффициент расходомера.

Минимальный протокол:

1. Контроллер отправляет пакет телеметрии с номером и временем.
2. Сервер проверяет ключ устройства, диапазоны и защиту от повтора.
3. FAO-56 остаётся основным расчётом; датчик используется для проверки и
   корректировки наблюдаемого начального состояния.
4. При необходимости полива Telegram показывает причину, объём и время насоса.
5. Человек подтверждает запуск. Сервер создаёт ограниченную по времени команду.
6. Контроллер включает реле, считает импульсы расходомера и отправляет итог.
7. Локальные защиты выключают помпу даже без связи: максимальное время,
   отсутствие потока, пустой бак, повторная команда и аварийная кнопка.

**Готово, когда:** симулятор устройства проходит тот же API без Arduino; потеря
интернета не оставляет помпу включённой; повтор команды не включает её второй раз.

### Этап E. Доказательный эксперимент

1. Создать эксперимент с вариантами `Su-Tech` и `контроль`.
2. Записывать фактически поданную воду и энергию, а не только прогноз модели.
3. Добавить наблюдения растений: высота, число листьев, признаки стресса и фото.
4. Показать графики по дням: ET0/осадки, дефицит/RAW, литры, кВт·ч и рост.
5. Экспортировать анонимизированный CSV и готовую таблицу для научной статьи.

**Готово, когда:** любое число на конкурсном слайде можно проследить до сырого
измерения, формулы, версии расчёта и даты.

### Этап F. Финальная проверка и публикация

1. Запустить unit, интеграционные, миграционные и frontend-тесты в GitHub Actions.
2. Добавить тестовый контур: тестовый бот, тестовая база и симулятор ESP32.
3. Провести smoke-test production: `/health`, меню Telegram, WebApp RU/KZ,
   Open-Meteo, сохранение поля, следующий день, полив и CSV.
4. Опубликовать backend, проверить SHA ревизии и только затем переключить бота.
5. Заморозить конкурсный релиз тегом и сохранить экспорт экспериментальных данных.

## 4. Definition of Done программной части

- Все данные переживают рестарт и деплой.
- Ни один расчёт не выполняется дважды за дату.
- Все значения имеют единицы, диапазоны и версию формулы.
- Отрицательная экономия не скрывается; сценарии сравнивают один дефицит.
- Рекомендация и фактический полив являются разными событиями.
- Устройство не может включить помпу без авторизации и временного ограничения.
- RU/KZ интерфейсы проходят одинаковые сценарии.
- Ошибка погоды или датчика явно показана и не заменяется фиктивными числами.
- Экспериментальные показатели отделены от модельных прогнозов.
- Production SHA, состояние базы и последний ежедневный запуск наблюдаемы.

## 5. После этого в реальной жизни останется

1. Собрать и безопасно запитать низковольтный стенд.
2. Откалибровать датчик влажности и расходомер по мерной ёмкости.
3. Измерить фактическую мощность и производительность мини-помпы.
4. Провести повторяемый опыт Su-Tech против контрольного полива.
5. Собрать фотографии, видео, сырые данные и подписи наблюдений.
6. Подготовить демонстрационный сценарий и резервный офлайн-режим выставки.
