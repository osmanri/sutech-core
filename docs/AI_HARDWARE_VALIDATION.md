# Проверка ИИ-агронома и поливочного стенда

## Программные проверки ИИ-агронома

```bash
cd serverless
node --experimental-loader ./test/sdk-loader.mjs --test test/diagnosis-guardrails.test.js
```

- Пустой файл, неподдерживаемая сигнатура и файл больше 4 МиБ отклоняются до обращения к ИИ. Проверка JPEG и PNG основана на сигнатуре. Допустимая сигнатура сама по себе не подтверждает читаемость изображения или наличие растения в кадре.
- При неизвестной культуре или состоянии, смешанных признаках, плохом качестве и общей неопределённости бот не передаёт Gemini предположения классификатора. В экспериментальном режиме ответ сообщает, что распознавание не дало результата. Оценка видимых признаков остаётся предварительной.
- При ошибке сети, недопустимом ответе или превышении срока ожидания классификатора бот может получить предварительную оценку Gemini. Среда без таймеров сразу переходит к этому варианту. Если оба сервиса недоступны, исходное сообщение сохраняется в чате для повтора. В истории не появляется успешный разбор.
- Тесты подставляют ответы внешних сервисов и выполняют настоящий расчёт полива через бота. Отказ сервисов ИИ и ответ по фото не меняют сохранённые поля, записи о поливах или рассчитанные объёмы. Новый расчёт для тех же условий даёт те же объёмы. Связь ИИ с реле отсутствует.

Эти сценарии проверяют обработку данных приложением. Для оценки качества распознавания нужны размеченные фотографии и независимая проверка экспертом. Пределы сетевых сроков на Telegram Serverless описаны в [проверке надёжности сервисов](SERVICE_RELIABILITY.md).

## Программные проверки прошивки

Сценарии и команда запуска находятся в [инструкции к host-тесту](../firmware/host_test/README.md). Тест подставляет импульсы, время, EEPROM и состояние выводов. Он проверяет остановку по `STOP`, достижению заданной дозы и 30-секундному таймеру при нулевом или частичном потоке. Возобновить отсчёт повторной командой запуска или обнулить счётчик во время подачи нельзя. Тайм-аут по объёму отключает вывод реле до звукового сигнала.

Программный предел одной дозы составляет 1000 мл. Команда `FLOW_CAL` использует импульсы последнего завершённого запуска по времени. После неудачной калибровки сохраняется предыдущий коэффициент, если он был корректным. Нечисловые значения и коэффициент, при котором счётчик переполнится на максимальной дозе, отклоняются. Ошибочно записанную, но правдоподобную величину из мерного цилиндра прошивка определить не может.

Сборка скетча для Arduino Uno выполняется отдельно от host-теста.

```bash
arduino-cli compile --fqbn arduino:avr:uno firmware/arduino_relay_pump
```

## Измерения на стенде

Для физической проверки собранного стенда нужны результаты с указанием версии прошивки, модели платы, условий, числа повторов и измерительного прибора.

| Сценарий | Что измерить |
| --- | --- |
| Запуск и сброс платы, ручная остановка | Состояние реле на запуске и сбросе. Задержку от получения `STOP` до выключения реле и прекращения потока. |
| Пропадание сигнала расходомера | Время отключения после запуска и объём, фактически прошедший в мерный сосуд, с потерей сигнала с начала и в середине подачи. Сопоставить со счётчиком и причиной остановки. |
| Калибровка и точность доз | По независимой мерной ёмкости или весам измерить фактические объёмы нескольких повторов на малой, средней и предельной дозе. Записать отклонения, разброс и сохранение коэффициента после сброса. |
| Низкий уровень воды и отказ датчика | Проверить порог запуска обычной команды и фактическое состояние реле при обрыве датчика. |

30 секунд — порог в цикле программы. Обработка последовательного порта, опрос датчиков и переключение реле влияют на физическое время отключения. `WATER_FORCE` предназначена для ручной проверки и обходит датчик уровня. Измерений стенда для этих сценариев пока нет.
